# 法令データ 取り込み実行ガイド

取得済みの一括 Zip を DB に投入する `laws-ingest bootstrap` の運用手順。**全件をまとめて
取り込む初期ブートストラップ**を中心にまとめる。

- 取得（landing zone への着地）は [`ダウンロード実行ガイド.md`](./ダウンロード実行ガイド.md) を参照（本ガイドの前段）。
- 設計上の位置づけは [`docs/design/13-初期取り込み.md`](../design/13-初期取り込み.md)（Stage 1→Load→索引後構築）。

## 全体の流れ

```
download（取得）  →  bootstrap（取り込み）  →  /health/ingest（確認）
  一括 Zip            parse → load →            取り込み状態の集約
  を landing へ        text_search 生成
```

## 前提

- `uv sync` 済み（`.venv/bin/laws-ingest` が生成される）。
- DB が起動し、**マイグレーション適用済み**であること。
  - compose: `docker compose up -d postgres migrate`（`migrate` が `alembic upgrade head` を実行して終了）。
  - 直接: `uv run alembic upgrade head`。
- 取り込む Zip が landing zone に着地済み（取得手順は前段ガイド）。

## 全件をまとめて取り込む（初期ブートストラップ）

### 1. 全件 Zip を取得する

```bash
# 全件・XML のみ（GB 級の実通信。--section 1 が既定）
uv run laws-ingest download --section 1
```

着地先（例）:

```
var/landing/raw/bulk/{取得日}/section1/
├── all_xml.zip            # 全法令の XML を含む一括 Zip
└── all_xml.zip.meta.json  # sha256 / byte_size / source_url など
```

### 2. 全件を投入する

取得した `all_xml.zip` を `bootstrap` に渡すと、Zip 内の**全法令を 1 回で投入**する。

```bash
uv run laws-ingest bootstrap var/landing/raw/bulk/{取得日}/section1/all_xml.zip
```

このコマンドが行うこと（設計 §13）:

- **二次索引を DROP → 全件投入 → 後構築**（既定。空 DB へのバルク投入を高速化、§13.4）。
- **1 法令 = 1 トランザクション**で投入し、個別の失敗は `ingest_law_event` に記録して継続（警告継続、§11.12.3）。途中の 1 件が落ちても全体は止まらない。
- 索引 CSV から分類・改正法令メタを充足し、施行期間（`enforcement_period`）・現行最新フラグ（`is_current_latest`）を計算（A-1 / A-2）。
- `law_node` は COPY でバルク投入、`text_search`(tsvector) を法令単位で生成。

完了すると標準出力にサマリ JSON が出る:

```json
{
  "ingest_run_id": 1,
  "total": 12345,
  "inserted": 12340,
  "failed": 5,
  "node_count": 9876543,
  "failures": [["{law_revision_id}", "エラー要約"], ...]
}
```

終了コードは **`failed == 0` で `0`、失敗があれば `1`**。

> ⚠️ 全件は GB 級・数百万ノードになり、取り込みには相応の時間がかかる。実測の目安は
> [`docs/design/13-初期取り込み.md`](../design/13-初期取り込み.md) §13.10 を参照。

### 3. 取り込み結果を確認する

```bash
# API 経由（compose の api、または uvicorn 起動時）
curl -s localhost:8000/health/ingest | jq .
# → {"status":"ok","total_runs":1,"last_run":{"kind":"full","status":"success",...},...}
```

`failed > 0` や `status` が `ok` 以外なら、失敗法令を `ingest_law_event` から特定して再投入する（下記）。

## コンテナ（compose）で取り込む場合

compose の `worker` は**日次差分（03:00）を自動取り込み**するが、初期の全件ブートストラップは
landing zone（ホストの `var/`）にある Zip を使うため、**ホスト側で `uv run laws-ingest …` を
実行するのが簡単**。コンテナ内で動かす場合は `var/` をボリュームとしてマウントする必要がある
（既定の compose では未マウント。landing zone の外部化は Issue #4 で扱う）。

```bash
# 取得・取り込みはホストで（DB は compose の postgres を使う）
uv run laws-ingest download --section 1
uv run laws-ingest bootstrap var/landing/raw/bulk/{取得日}/section1/all_xml.zip
```

## 分類別に分けて取り込む（任意）

全件が重い、または一部だけ試したいときは分類別（`--section 2`）に分けて取得・投入してもよい。
結果は全件投入と同じテーブルに入る。

```bash
uv run laws-ingest download --section 2 --category 1     # 例: 分類 1（憲法・小サイズ）
uv run laws-ingest bootstrap var/landing/raw/bulk/{取得日}/section2/1_xml.zip
```

スモークテストにも使える（小さい分類で一連の流れを確認してから全件に進む）。

## 再取り込み・冪等性

- **冪等**: 同一 `law_revision_id` は `law` / `law_revision` の UPSERT＋`law_node` の洗い替えで再実行しても同じ結果になる（§13.7）。同じ Zip を投入し直しても重複しない。
- **失敗法令だけ再投入**: `ingest_law_event` で失敗を特定できる。

  ```sql
  SELECT law_revision_id, error
  FROM ingest_law_event
  WHERE ingest_run_id = <run_id> AND action = 'failed';
  ```

  原因を直したうえで、対象 Zip を再度 `bootstrap` すれば該当法令が UPSERT される。

## オプション

| オプション | 用途 |
|---|---|
| （既定） | 索引 DROP→後構築・COPY 投入で全件を高速に入れる |
| `--keep-indexes` | 二次索引を保持したまま投入（少量・追加投入向け。差分ジョブはこちら） |
| `--no-copy` | COPY ではなく INSERT で投入（性能比較用） |

> 日次差分（`enqueue-delta` / ワーカーの `@periodic`）は索引を保持して投入する（差分は DROP しない）。全件の初期投入だけが索引 DROP→後構築を使う。
