# 運用ガイド（監視・ログ・バックアップ）

本番運用での監視・ログ・バックアップ／リストアの手順をまとめる（C 系）。設計上の根拠は
`docs/design/` を、実装状況は `CLAUDE.md` / `README.md` を参照。

## 1. ヘルスチェック / 監視（C-1 / C-3）

外形監視・コンテナのプローブには以下のエンドポイントを使う。

| エンドポイント | 用途 | 正常 |
| --- | --- | --- |
| `GET /health` | プロセス生存（liveness） | `{"status":"ok"}` |
| `GET /health/db` | DB 疎通（readiness） | `{"database":"ok"}` |
| `GET /health/ingest` | 取り込みの健全性 | `status` が `ok` |

### `/health/ingest` のレスポンス

`ingest_run` / `ingest_law_event` を集約し、取り込みが正常に回っているかを返す。

```json
{
  "status": "ok",
  "total_runs": 12,
  "last_run": {
    "id": 12,
    "kind": "delta",
    "status": "success",
    "started_at": "2026-06-13T03:00:01+00:00",
    "finished_at": "2026-06-13T03:02:10+00:00",
    "stats": {"total": 30, "inserted": 30, "failed": 0, "node_count": 1234}
  },
  "last_success_at": "2026-06-13T03:02:10+00:00",
  "recent_failures": 0,
  "failed_samples": []
}
```

`status` の意味:

- `never`   : 取り込み実行が 1 件も無い（初回 bootstrap 前）。
- `running` : 直近の実行が進行中。
- `failed`  : 直近の実行が失敗で終了。
- `stale`   : 最後の成功が鮮度ウィンドウ（既定 48h、`INGEST_FRESHNESS_HOURS`）より古い。**日次差分が止まっている疑い**。
- `ok`      : 鮮度ウィンドウ内に成功した実行がある。

**アラート方針**: `status` が `ok` 以外、または `recent_failures > 0` を異常として通知する。
日次差分（03:00）が動かなくなると翌々日の朝に `stale` へ落ちるため、しきい値はそれより
短い監視間隔にする。

### ワーカー（Procrastinate）の監視

ジョブの滞留・失敗は専用スキーマのテーブルで確認できる。

```sql
-- 失敗・滞留しているジョブ
SELECT id, task_name, status, attempts, scheduled_at
FROM procrastinate.procrastinate_jobs
WHERE status IN ('failed', 'todo')
ORDER BY id DESC LIMIT 50;
```

## 2. 構造化ログ（C-2）

API・取り込み CLI・ワーカーは JSON 行ログを標準出力に出す（追加のログ基盤に流し込みやすい）。

```json
{"ts":"2026-06-13T03:02:10.123+00:00","level":"INFO","logger":"laws_api_mirror.ingest.bootstrap","message":"ingest.run.finished","run_id":12,"kind":"delta","total":30,"inserted":30,"failed":0,"node_count":1234,"text_searched":1200}
```

主なイベント名:

- `ingest.run.started` / `ingest.run.finished` … 取り込み実行の開始・終了（件数つき）。
- `ingest.law.failed` … 法令単位の取り込み失敗（`law_revision_id` / `error`）。
- `ingest.daily_delta.started` / `ingest.daily_delta.finished` … 日次差分ジョブ。

設定（環境変数 / `.env`）:

- `LOG_LEVEL`（既定 `INFO`）
- `LOG_JSON`（既定 `true`。`false` で人間可読フォーマット）

## 3. バックアップ / リストア（C-4）

ミラーの内容は再取得可能（e-Gov から再ダウンロード→再投入）だが、全件 bootstrap は時間が
かかるため、定期バックアップで復旧時間を短縮する。

### 前提（カスタム拡張）

DB は `pg_bigm` / `ltree` / `btree_gist` を使うカスタムイメージ（`docker/postgres/`）。
**リストア先も同じ拡張が入ったイメージ**であること。`pg_dump` は拡張の中身ではなく
`CREATE EXTENSION` 文を出力するため、拡張バイナリ自体は復元先に存在している必要がある。

### バックアップ（論理ダンプ）

カスタム形式（`-Fc`）で取得すると並列リストア・部分リストアができる。

```sh
# compose 環境の例（サービス名 postgres、DB 名 laws）
docker compose exec -T postgres \
  pg_dump -U laws -d laws -Fc --no-owner --no-privileges \
  > backup/laws_$(date +%Y%m%d).dump
```

`procrastinate` スキーマのジョブ履歴は復旧に不要なら除外してよい:

```sh
docker compose exec -T postgres \
  pg_dump -U laws -d laws -Fc --no-owner --exclude-schema=procrastinate \
  > backup/laws_data_$(date +%Y%m%d).dump
```

### リストア

```sh
# 空の DB を用意（既存を捨てる場合）
docker compose exec -T postgres psql -U laws -d postgres \
  -c "DROP DATABASE IF EXISTS laws;" -c "CREATE DATABASE laws OWNER laws;"

# 並列リストア（-j はコア数に合わせる）
cat backup/laws_20260613.dump | docker compose exec -T postgres \
  pg_restore -U laws -d laws --no-owner --no-privileges -j 4
```

リストア後の確認:

```sh
# スキーマ整合（未適用マイグレーションが無いこと）
uv run alembic current
# 取り込み状態
curl -s localhost:8000/health/ingest | jq .status
```

### 代替: 再取得による復旧

バックアップが無い／古い場合は、e-Gov から取り直して再投入する。

```sh
uv run laws-ingest download --section 1            # 全件 Zip を取得
uv run laws-ingest bootstrap var/landing/<zip>     # 全件投入（索引は DROP→後構築）
```

差分のみ取りこぼした場合は対象日を指定して差分投入:

```sh
uv run laws-ingest enqueue-delta --update-date 20260613   # ワーカー稼働時
```
