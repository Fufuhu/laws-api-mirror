## 13. 初期データ取り込み（ブートストラップ）方式

§12 で取得した全件 Zip を、**空の DB へ初回投入する**方式を定める。下流のスキーマは §4、パース実装方針は §2.7・§8、ジョブ基盤は §11.7、再実行性は §11.3、完全性検証は §12.5 を前提とする。本章は **「空 DB への一括ロードをどう速く・安全に・再開可能に行うか」** に集中する。

### 13.0 確定スコープ

| 項目 | 決定 | 根拠 |
|---|---|---|
| 実行方式 | **ハイブリッド（方式 C）**: 取得・展開・fan-out・検証は Procrastinate、`law_node` ロードのみ COPY バルク | §13.2 |
| 索引・制約・検索索引 | **ロード後に一括構築**（素 INSERT/COPY → 後構築） | §13.4 / §13.6 |
| 競合制御 | 空 DB のため **UPSERT 不要・素 INSERT**（重複は事後の UNIQUE 索引構築で検出） | §13.5 |
| パース層 | 日次差分（§8）と**共有**。ロード戦略のみ初期専用に分岐 | §13.2 |
| 対象 | 現行の有効な法令のみ・現行版スナップショット（§12.0） | §12 |

### 13.1 初期取り込みが日次差分と異なる前提

| 観点 | 初期ブートストラップ | 日次差分（§8） |
|---|---|---|
| DB 状態 | 空（既存行ゼロ） | 既存データあり |
| 競合 | UPSERT 不要（素 INSERT） | `law_revision_id` で UPSERT 必須 |
| 件数 | 全件（約 1 万法令 / `law_node` 数百万〜数千万行） | 数件〜数百件 |
| 実行回数 | 一度きり（＋月次リフレッシュ、§12.8） | 毎日 |
| 索引 | **ロード中は外す**（後構築） | ライブ（即時検索性優先） |
| 最適化余地 | 大（COPY・遅延索引・並列） | 小 |

この差を活かし、初期だけ PostgreSQL のバルクロード定石（**素 INSERT/COPY ＋ 二次索引の後構築 ＋ 制約の遅延検証**）を適用する。

### 13.2 実行方式（ハイブリッド C）

オーケストレーション（取得・展開・完全性検証・再開）は Procrastinate に任せ、**最も重い `law_node` 投入だけを空 DB 最適化したロード相**として分離する。パース層（`lxml.iterparse`、§2.7）は日次差分と共有し、**差し替えるのはロード戦略のみ**。

```
Procrastinate オーケストレーション（粗粒度ジョブ）
  Stage 0 Fetch ──→ Stage 1 Unpack/Inventory ──→ [ロード相] ──→ Stage I Index ──→ Stage V Verify
                                                     │
              ┌──────────────────────────────────────┘
              ↓  ロード相（空 DB 最適化・索引なし）
   Phase A  二次索引を外す（DROP INDEX / 制約 NOT VALID 化）
   Phase B  マスタ確認（node_kind / category / era … は Alembic 投入済み §2.6）
   Phase C  ヘッダ投入: amendment_law(プレースホルダ) → law → law_revision  ※小・素 INSERT
   Phase D  本文投入: law_node を COPY（並列ワーカー、索引なし）+ attached_file/S3(§12.6)
   Stage I  索引・制約・検索索引を一括構築（§13.4 / §13.6）
   Stage V  完全性検証・受け入れ判定（§13.8）
   Stage R  Lazy reconciliation（amendment_law.linked_law_id、§4.5 / §11.8）
```

**「親→子で 1 法令 = 1 ジョブ」にしない理由**（§11.7.6 の差分用設計との違い）: 1 万件の独立トランザクションを**ライブ索引のまま**コミットすると、GIN(`text_search`)・GiST(`path`) への逐次更新が律速になる。初期は索引を外した単一ロード相に集約し、並列は「**索引なしテーブルへの並行 COPY**」で得る（PostgreSQL は同一テーブルへの並行 COPY を許容）。Procrastinate は相（フェーズ）境界の管理・再開・観測に使い、法令単位の粒度ではワーカー内のバッチに委ねる。

### 13.3 投入順序と FK / 制約

FK 解決のため、テーブル投入は依存順に行う。索引が無くても **PK 索引は常に存在**するため、FK（`law_node.law_revision_id → law_revision`、`law_node.parent_id → law_node`）は解決できる。

```
1. マスタ（node_kind / category / era / law_type / repeal_status …）   ← Alembic 投入済み（§2.6）
2. amendment_law（プレースホルダ UPSERT。最低限 amendment_law_id のみ確定、§4.5-3）
3. law
4. law_revision（amendment_law を先行投入済みなので FK 解決可。§4.5）
5. law_node（COPY、並列、二次索引なし）
6. attached_file（§12.6。バイナリは S3 へ、行は sha256 重複排除）
```

- **`EXCLUDE USING gist`（`enforcement_period` の重複防止、§4.3）** はロード中は外し、Stage I で付与（`ALTER TABLE ... ADD CONSTRAINT`。現行版のみなので 1 法令 1 区間が基本で衝突は起きない想定だが、制約付与時に検証される）。
- **`UNIQUE (law_revision_id, path)`（§4.7）** はロード中は張らず、Stage I で **UNIQUE 索引として後構築**する。これがパーサのパス生成バグ（重複パス）の検出器も兼ねる。
- 現行版のみのため `enforcement_period` は最新区間 `[date, infinity)` を全行に設定（§4.3）。

### 13.4 パフォーマンス設計（ロード相 ＋ Stage I）

- **COPY 投入**: `law_node` は `asyncpg` の `copy_records_to_table`（バイナリ）で流す。INSERT 文の往復を排し、数千万行のスループットを確保。パーサは `iterparse` で 1 法令ずつストリーム生成し、COPY バッファに詰める（メモリピークを抑制、§2.7）。
- **二次索引の後構築**: GIN(`text_search`) / GIN(`attrs` jsonb_path_ops) / GiST(`path` ltree) / btree 各種は **Phase A で DROP（または最初から張らない）→ Stage I で `CREATE INDEX`**。空テーブルからの一括構築は、ライブ更新の累積より桁で速い。
- **`maintenance_work_mem` 一時拡大**: Stage I の `CREATE INDEX` 直前にセッションで拡大し、外部ソートのディスクスピルを抑える。完了後に戻す。
- **WAL / コミット**: ロード相のセッションで `synchronous_commit = off`（クラッシュ時は landing zone から再実行可能なので許容、§12.4）。可能なら `wal_compression` 等は環境ポリシーに合わせる。**`UNLOGGED` 化は採用しない**（クラッシュ耐性とレプリカ整合を損なうため）。
- **並列度**: パース＆COPY ワーカー数は「コア数 − 余裕」を上限に環境変数で調整（§11.1 の Python トークナイザ Docker 同梱方針と整合）。I/O とパース CPU のバランスを初回計測でチューニング。
- **バッチコミット境界 = 法令境界**: COPY のコミットは N 法令ごと。**境界を法令にそろえる**ことで、失敗時に「どの法令まで確定したか」が `ingest_law_event` で一意に追え、再開が容易（§13.7）。

### 13.5 マスタ・参照データの扱い

`node_kind` / `category` / `era` / `law_type` / `repeal_status` / `amendment_type` 等の参照テーブル（§4.1）は **Alembic リビジョンの `op.bulk_insert` で投入済み**（§2.6）であることを Phase B で前提確認する。ブートストラップはこれらをロードしない（マイグレーションの責務）。未知要素（XSD 差分）に遭遇した場合は `unknown_node_kinds` 観測テーブルに記録し、警告＋閾値モードで継続（§11.12.3）。

### 13.6 検索索引（`text_search`）の後構築

§11.1 の「`GENERATED ... STORED` にせず、取り込み時に Python トークナイザ出力を `text_search` へ書き込む」方針と整合させ、初期は**ロード後の別パス**で一括生成する。

1. ロード相では `text_plain`（インライン要素を剥がしたプレーンテキスト、§4.7）までを投入し、`text_search` は NULL のまま。
2. Stage I で `fugashi`（MeCab）トークナイズ → `to_tsvector('simple', ...)` 相当を**バルク UPDATE**で `text_search` に書き込む（§11.1 の方式 B）。
3. 書き込み後に GIN(`text_search`) と、`text_plain` への pg_bigm GIN を `CREATE INDEX`。

辞書バージョンは `text_index_meta`（§11.1）に記録し、再生成時の再現性を担保する。

### 13.7 冪等性・再実行性

§11.3 / §12.5 の枠組みに乗せる。

- **成果物の記録**: `download_artifact`（§12.5）で生 Zip を、`ingest_run` / `ingest_law_event`（§4.9）で法令単位の成否を記録。
- **スキップ判定**: `law_xml.xml_sha256` が既存と一致する法令は再投入をスキップ（差分・月次リフレッシュ時に効く。初回は全件 INSERT）。
- **再開（中断 → 再実行）**:
  - ロード相が法令 7,000/10,000 で落ちた場合、`ingest_law_event` で `inserted` 済みの法令を除外し、未処理分から再開。バッチ境界が法令境界なので、確定済みデータと未確定データが混在しない。
  - **索引未構築のまま中断**しても、再開はロード相の続きから。Stage I は全件ロード完了後に一度だけ走る。
- **全面やり直し**: パーサ改修などで作り直す場合は、ドメインテーブルを `TRUNCATE`（CASCADE）して再ロード。**landing zone の生 Zip は保持**しているため e-Gov へ再アクセスしない（§12.4）。Procrastinate のジョブ状態もリセットする手順を Runbook 化。

### 13.8 受け入れ基準（Stage V 検証）

ブートストラップ成功の判定を定義する。

1. **件数突合**: `download_artifact.law_count`（Zip 内法令フォルダ数＝期待値）と `ingest_law_event` の成功件数が一致（§12.5）。差分は再投入。
2. **XSD 検証率**: 警告＋閾値モードで、検証失敗が閾値（既定 5%、§11.12.3）未満。超過なら停止し原因調査。
3. **ラウンドトリップ抽出検査**: 代表法令 10〜20 件で、`law_node` から再構築した XML が原文（`law_xml.xml_gz`）と構造的に一致することを確認（レンダリング層 §11.10.4 の早期検証も兼ねる）。
4. **索引の健全性**: Stage I で作成すべき索引・制約がすべて存在し `VALID` であること（部分作成で止まっていないか）。
5. **`elm` 解決スモークテスト**: 数件の `elm=MainProvision-Article_N-...` が `path <@` で正しいサブツリーを返す（§7.4）。

### 13.9 失敗時の扱い

- **個別法令の失敗**: パース/検証失敗は `ingest_law_event.action='failed'＋error` に記録して**継続**（警告＋閾値、§11.12.3）。閾値超過で相を停止。
- **Stage I の失敗**: 索引構築の途中失敗は、対象索引を `DROP` して再実行（冪等）。`CREATE INDEX CONCURRENTLY` は初回（空 DB・無停止不要）では使わず、通常の `CREATE INDEX` で高速構築する。
- **相全体の中断**: ロード相の致命的失敗は、ドメインテーブル `TRUNCATE` → landing zone から再ロード（§13.7）。

### 13.10 体積・所要時間の見積もり

- 法令: 約 1 万件（現行）。`law_node`: 数百万〜数千万行（§11.1 / §12.9）。
- ロード相（COPY・索引なし）と Stage I（索引・`text_search` 構築）のどちらが律速かは規模・構成依存。下記実測では **text_search のトークナイズ（fugashi）と GIN 索引再構築が支配的**。

#### 13.10.1 実測ベンチマーク（COPY vs INSERT）

事項別分類「国税」（`category_cd=13`、459 リビジョン、巨大法令を多く含む）を 1 分類ぶん投入した実測値。`law_node` 投入を **COPY**（`copy_records_to_table`）と **INSERT**（`executemany`）で比較。いずれも二次索引 DROP→後構築・`text_search` 生成を含む全工程。

| 投入方式 | law_node 行数 | 所要時間 | ピーク RSS |
|---|---|---|---|
| **COPY**（既定） | 8,485,078 | **9 分 29 秒** | 約 2.08 GB |
| INSERT（`--no-copy`） | 8,485,078 | 18 分 08 秒 | 約 2.09 GB |

- 計測環境: ローカル Docker（PostgreSQL 16、pg_bigm/ltree）、`bootstrap` を素実行（並列なし）。
- **COPY は INSERT の約 1.9 倍高速**（8.5M 行規模）。差は `law_node` 投入区間で生じ、`text_search` 生成・索引再構築の所要は両者共通。
- メモリは **1 法令 = 1 トランザクション**で頭打ち（最大の単一法令の DOM ＋行バッファがピーク）。corpus 全体が増えてもピークは概ね不変。
- スループット概算: 約 14,900 行/秒（parse＋tokenize＋COPY＋索引再構築込み）。全件（`file_section=1`、数千万〜1 億行規模）なら **COPY で概ね 1〜2 時間**の見込み。
- 投入後の検索性能: 8.5M 行に対する `pg_bigm` の `LIKE`（GIN 利用）が 0.3 秒台。

#### 13.10.2 実測（全件 file_section=1）

現行法令の全件（`file_section=1`、XML のみ）を 1 回でブートストラップした実測値。COPY（既定）・並列なし。

| 項目 | 値 |
|---|---|
| ダウンロード | 284 MB / 10,190 リビジョン |
| 投入時間（bootstrap） | **32 分 24 秒** |
| ピーク RSS | 約 4.3 GB |
| `law_node` 行数 | 28,409,763（約 2,840 万） |
| 法令数 / リビジョン数 | 8,963 / 10,180（後述の修正後は 10,190 = 100%） |
| `text_search` 生成行 | 12,763,901 |
| 投入後の検索 | 28.4M 行に対する `pg_bigm` `LIKE` が 0.2 秒前後 |

- スループット約 14,600 行/秒（§13.10.1 の分類別実測と整合）。当初見積りの「1〜2 時間」より速く **約 32 分**。平均的な法令は国税分類ほど巨大でないため。
- メモリは 1 法令 = 1 トランザクションで頭打ち（最大単一法令で約 4.3 GB）。
- **データ起因のエッジケースを 2 件検出**（全件規模でのみ顕在化、初回は 10/10,190 失敗 → 修正後 0 失敗）:
  - `law_node` の `path` 重複: 採番サフィックスが実在の枝番ラベルと衝突（`Num="23"`×3 ＋ `Num="23_2"`）。`_assign_labels` を衝突回避に修正。
  - `law.law_num` の重複: 異なる `law_id` が同一 `law_num` を持つ（人事院規則・省令）。`UNIQUE` を撤廃し非ユニーク索引に（§4.2 / migration 0003）。

#### 13.10.3 さらなる高速化の候補（未実施）

- `text_search` トークナイズの並列化（律速のひとつ。§11.1-4）。
- 法令単位ではなくバッチ単位の COPY、`maintenance_work_mem` の一時拡大（§13.4）。
- 並列ワーカーによる「索引なしテーブルへの並行 COPY」（§13.2）。

### 13.11 残課題 / 要実機確認

1. **二次索引を「外す」実装手段**: 完全スキーマで `DROP INDEX` → 後 `CREATE` か、ロード用に PK/FK のみの最小スキーマを当てて後追いマイグレーションで索引追加か。Alembic 運用（§2.6）との整合で決定。
2. **並列度と COPY 形式**: ワーカー数、バイナリ COPY vs テキスト COPY の実測比較。
3. **`text_search` 構築コスト**: トークナイズのバルク処理時間とメモリ。Stage I を法令範囲で分割並列するか。
4. **`EXCLUDE` 制約付与のコスト**: 現行版のみで衝突は無い想定だが、付与時検証の所要を計測。
5. **ラウンドトリップ検査の合否基準**: 構造一致の判定粒度（空白・属性順の正規化、§11.11）。
6. **月次全件リフレッシュとの共通化**: リフレッシュ時は既存データありのため、初期専用の「索引を外す」最適化をどこまで流用するか（差分が小さければ通常 UPSERT 経路に寄せる）。
