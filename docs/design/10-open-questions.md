## 10. 未確定事項（要確認）

1. ~~**添付ファイルの保存先**~~ → **確定**: オブジェクトストレージに保存（DB の BYTEA には入れない）。本番（サーバー環境）は **AWS S3** をそのまま利用、開発・CI・オンプレ評価環境は **SeaweedFS**（S3 互換）を利用。MinIO はパブリックアーカイブ状態のため不採用。詳細は §11.2。現時点で CDN／署名付き URL は対象外。
2. ~~**全文検索エンジン**~~ → **確定**: `pg_bigm` + `tsvector` のハイブリッド構成（§5）。pgroonga はマネージド DB の互換性懸念から不採用。MeCab 辞書のバージョン管理運用は §11.1 で別途検討。
3. ~~**html/rtf/docx ファイル形式の生成**~~ → **1st リリースでは非対応**: 1st リリースは検索 API の提供を主目的とするため、`/law_file/{file_type}` でサポートするのは **`xml` と `json` のみ**。`html` / `rtf` / `docx` をリクエストされた場合は **400 Bad Request** で `unsupported file_type` 相当のエラーを返す（API §7 に反映）。将来要件として追加する可能性はあり、検討メモを §11.10 に残置。
4. ~~**キャッシュ層**~~ → **方針確定**: CDN は **通信経路最適化（TLS 終端・エッジ転送）目的のみ**で挟む。積極的なレスポンスキャッシュ（`Cache-Control: s-maxage` 等によるエッジ保持）は初期リリースでは行わない。**Redis は使用しない**（ジョブキュー §11.7 で確定済みの方針と統一）。アプリケーション層のキャッシュも初期は導入せず、必要性が観測されてから検討する。
5. ~~**更新頻度**~~ → **確定**: **日次 1 回**で十分。Procrastinate の `@periodic(cron="0 3 * * *")` で差分取り込みジョブを定期実行する（§8、§11.7）。e-Gov 側の差分提供範囲も過去 3 か月なので、日次運用していれば取りこぼしは発生しない。
6. ~~**既存改正法令の参照整合性**~~ → **確定**: 独立 `amendment_law` テーブル + Lazy reconciliation（方針 C + D、§11.8）。データモデルは §4.5 に反映済み。残課題は §11.8.4（新規制定法令の `amendment_law_id` 扱い、UPSERT 仕様、Lazy ジョブの頻度）。
7. ~~**`QuoteStruct` の取り扱い深度**~~ → **確定**: 方針 D（A → C 段階導入、§11.9）。初期は不透明 XML として保持（方針 A、§4.7 既存）、後段で §11.5 と連動して `quote_extract` テーブル（方針 C）を追加。
8. ~~**`AmendProvision` ツリーのレンダリング**~~ → **確定**: 1st リリースは **e-Gov API v2 互換維持**を前提とし、以下のみ実装する。
   - (a) `omit_amendment_suppl_provision=true` のサポート（`SupplProvision.Type='Amend'` のサブツリーを除外する SQL）
   - (b) AmendProvision / NewProvision ノードはそのまま JSON/XML レスポンスに含める（DB に格納した `law_node` を素直に返却）
   - 追加のレンダリング機能（改正指示と新条文の視覚的識別フラグ、改正前後差分生成 など）は **1st リリース対象外**。検討メモは §11.4 に残置。
9. ~~**JSON（詳細版/簡易版）の差分**~~ → **確定**: 1st リリースは **インタフェース互換のみ維持**する。
   - `json_format=full` / `light` の両方を受け付け、レスポンスは仕様で定められた**形状**（`full` は `{tag, attr, children}` ツリー、`light` は `{TagName: value or array}`）で返す。
   - レスポンスの **詳細内容（インライン要素の埋め込み表記、`light` でフィールド化する属性の選び方等）は、最も実装が容易な方針**を採用する。e-Gov 実 API とのバイト単位一致は目指さない。
   - 想定実装:
     - `full`: `law_node` ツリー（`raw_xml` を含む）から機械的に `{tag, attr, children}` を生成。
     - `light`: 構造ノードは `{TagName: [...]}` で再帰、インライン要素は `text_plain` をそのまま埋め込み、属性は API ドキュメントに明示された `AmendLawNum` / `Extract` / `Paragraph.Num` のみフィールド化、その他は破棄。
   - 厳密準拠のためのエッジケース（Ruby の括弧表記、ArithFormula のテキスト化、属性出力位置 等）は §11.11 に検討メモを残置し、必要に応じて将来リリースで合わせ込む。
10. ~~**XSD バージョン管理**~~ → **方針確定（運用設計は §11.13）**: 「XSD は不変ではなく、いずれバージョンアップする」前提で、(a) アップグレード検知、(b) `node_kind` 追加の Alembic リビジョン運用、(c) 妥当性検証ポリシー（厳格／警告／警告＋閾値）、(d) 過渡期の両バージョン対応、(e) コード・テストフィクスチャ追従、を**運用フローとして仕組み化する**。具体的な手順設計は §11.12。
