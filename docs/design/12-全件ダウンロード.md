## 12. 全件ダウンロード構成

すべての法令データをローカルに取得する際の構成を定める。取り込み（パース → DB UPSERT）の下流処理は §8 に、ジョブ基盤は §11.7 に、再実行性は §11.3 に委ね、本章は **「e-Gov からどう取得し、どこに着地させ、どう完全性を担保するか」** に集中する。

> 実装済みの取得コマンド（Stage 0: Fetch）の使い方は [`docs/guides/ダウンロード実行ガイド.md`](../guides/ダウンロード実行ガイド.md) を参照。

### 12.0 確定スコープ

§1・§8 および設計判断（本章作成時）により、以下を確定とする。

| 項目 | 決定 | 根拠 |
|---|---|---|
| 取得チャネル | **XML 一括ダウンロード（`/bulkdownload`）単独**。REST API v2（`/api/2/...`）はダウンロードに使わない | §12.1 |
| 取得する版 | **現行版スナップショットのみ**（過去リビジョンのバックフィルは行わない） | リクエスト数・ストレージを最小化 |
| 対象法令 | **現行の有効な法令のみ**（廃止・失効法令は対象外） | 1st リリースはミラーとして成立させることを優先 |
| 取得形式 | XML（`only_xml_flag=true`）＋ 添付ファイル（画像・様式）は別途取得（§12.6） | §4.8 / §11.2 |

**REST API v2 の位置づけ**: API v2 は本プロジェクトが **再提供する側**（§7）のインタフェースであり、**データ取得元としては使わない**。`/laws` や `/law_data` を法令単位でクロールする案は、現行版のみという要件に対して数千〜数万リクエストが必要となり、`/bulkdownload` の 1 リクエストに対して費用対効果が悪いため不採用とする（比較は §12.1）。

### 12.1 取得チャネルの決定（一括 Zip 単独）

データ取得経路には性質の異なる 2 つがあり、本章では **A（一括 Zip）に一本化**する。

| 観点 | A. 一括 Zip (`/bulkdownload`) | B. REST API v2 (`/api/2/...`) |
|---|---|---|
| 取得単位 | 全件まとめて 1 Zip | 法令・リビジョン単位で 1 リクエスト |
| 現行全件のリクエスト数 | 1〜数回 | 数千〜数万回（`/laws` 列挙 ＋ `/law_data` 個別取得） |
| 取得できる版 | 現行版スナップショット中心 | `law_revision_id` 指定で任意の過去リビジョンも可 |
| 添付ファイル | `only_xml_flag` を外せば pict 同梱 | `/attachment/{revision_id}` で個別取得 |
| 差分取得 | `file_section=3&update_date=` 過去 3 か月 | 更新日フィルタ ＋ 個別取得 |
| サーバ負荷 / 礼儀 | 低い（一括） | 高い（大量リクエスト、要レート制御） |

**決定理由**:

1. 確定スコープが「現行版スナップショットのみ」であり、過去リビジョンへ細粒度にアクセスする API の強みを必要としない。
2. `/bulkdownload` は数リクエストで全件が揃い、e-Gov 側への負荷・自前のレート制御コストが最小。
3. 既存設計 §8（取り込みパイプライン）が既に `/bulkdownload` を前提にしており、整合する。

将来「特定時点の条文（`asof`）を再提供したい」等で過去リビジョンが必要になった場合は、§12.7 の残課題として API 併用（チャネル B）を再検討する。

### 12.2 `/bulkdownload` エンドポイント仕様

実機（`https://laws.e-gov.go.jp/bulkdownload/`）および API ドキュメントから確認した仕様。

#### 12.2.1 パラメータ

| パラメータ | 値 | 意味 |
|---|---|---|
| `file_section` | `1` | **全件**（すべての法令データ） |
| | `2` | **分類別**（`category_cd` で指定。50 分類） |
| | `3` | **差分**（`update_date=YYYYMMDD` で指定。提供は過去 3 か月分） |
| `category_cd` | `001`..`050` | `file_section=2` のときの事項別分類コード |
| `update_date` | `YYYYMMDD` | `file_section=3` のときの基準日 |
| `only_xml_flag` | `true` | **XML のみ**取得（添付の画像・様式を含まない） |
| | 省略 / `false` | 画像・様式を含む**全データ**取得 |

URL 例:

```
# 全件・XML のみ
https://laws.e-gov.go.jp/bulkdownload?file_section=1&only_xml_flag=true

# 差分・XML のみ（日次運用）
https://laws.e-gov.go.jp/bulkdownload?file_section=3&update_date=20260613&only_xml_flag=true
```

#### 12.2.2 サイズ感

分類別ページの表示では「XML のみ」「全データ」の 2 サイズが並ぶ（例: 国税 82MB / 109MB）。全件（`file_section=1`）はこれらの合算規模で、**XML のみでも GB 級**になる見込み。したがって取得は「メモリ展開前提」ではなく **ストリーミング受信 → ディスク / オブジェクトストレージ着地**を前提に設計する（§12.4・§12.5）。

#### 12.2.3 Zip 内構造（暫定・要実機確認）

Web 上の利用報告より、**法令ごとにフォルダ（法令 ID）を持ち、その中に法令 ID 名の XML、添付がある場合は `pict/` 等のサブフォルダに画像・様式**が入る構造とされる。

```
all_xml.zip
├── 322CO0000000016/
│   └── 322CO0000000016.xml
├── 132AC0000000048/
│   ├── 132AC0000000048.xml
│   └── pict/
│       └── ....jpg
└── ...
```

正確なフォルダ階層・命名規則・空フォルダの有無・文字コードは **取得初回に実機の Zip を 1 本展開して確定**する（§12.8 要実機確認）。パーサ（§8）はこの構造に依存するため、構造定義は単体テストのフィクスチャ（代表数件）として固定する。

### 12.3 ダウンロードパイプラインの段構成

取得から DB 投入までを以下のステージに分ける。各ステージは Procrastinate のタスク（§11.7）として実装し、**Stage 0〜2 がダウンロード固有**、Stage 3 以降は §8 の取り込みパイプラインに接続する。

```
┌─────────────────────────────────────────────────────────────────┐
│ Stage 0  Fetch                                                   │
│   GET /bulkdownload?file_section=1&only_xml_flag=true            │
│   ストリーミング受信 → landing zone (S3) に生 Zip を保管          │
│   sha256 / byte_size / http_status を download_artifact に記録    │
└───────────────┬─────────────────────────────────────────────────┘
                ↓
┌─────────────────────────────────────────────────────────────────┐
│ Stage 1  Unpack & Inventory                                      │
│   生 Zip を展開し、法令 ID フォルダを列挙 → 目録(manifest)生成     │
│   期待法令数を ingest_run.stats に記録（完全性検証の基準）        │
└───────────────┬─────────────────────────────────────────────────┘
                ↓
┌─────────────────────────────────────────────────────────────────┐
│ Stage 2  Fan-out                                                 │
│   法令単位で子ジョブ enqueue（親→子、1 法令 = 1 子タスク §11.7）  │
└───────────────┬─────────────────────────────────────────────────┘
                ↓  （以降は §8 取り込みパイプライン）
       Stage 3 Parse (lxml.iterparse) → Stage 4 Load (UPSERT / COPY)
                                       → 添付ファイル S3 アップロード(§12.6)
                ↓
┌─────────────────────────────────────────────────────────────────┐
│ Stage 5  Verify                                                  │
│   manifest 期待件数 vs ingest_law_event 成功件数を突合           │
│   欠落・失敗を抽出し、再投入（§11.3）                            │
└─────────────────────────────────────────────────────────────────┘
```

- **Stage 0 と Stage 1 を分離**する意図は、巨大 Zip の取得（ネットワーク律速・失敗しやすい）と展開（CPU/IO 律速）を別ジョブにし、**取得済み Zip を再取得せずに再展開・再パースできる**ようにするため（冪等性、§12.5）。
- Stage 2 以降は **1 法令 = 1 トランザクション**（§8）で失敗を局所化する。1 法令のパース失敗が全件を巻き戻さない。

### 12.4 landing zone（生データ保管層）

ダウンロードした生 Zip（および展開後の生 XML）は、パース前に **オブジェクトストレージ（本番 S3 / 開発 SeaweedFS、§11.2）にそのまま退避**する。

**目的**:

1. **再パース冪等性**: パーサや `node_kind` を変更した際、e-Gov へ再アクセスせずに手元の生データから作り直せる。
2. **トレーサビリティ**: 「DB のこの行は、いつ取得したどの Zip 由来か」を `sha256` で追跡可能にする。
3. **障害分離**: 取得（外部依存・不安定）と取り込み（内部処理）を時間軸で分離し、e-Gov 側の一時障害がパイプライン全体を止めない。

**オブジェクトキー設計**:

```
raw/bulk/{captured_date}/section1/all_xml.zip          # 全件 Zip（生）
raw/bulk/{captured_date}/section3/{update_date}.zip    # 差分 Zip（生）
```

- `captured_date` は取得日（こちら側のタイムスタンプ）。同日複数回取得した場合は `sha256` 差分で重複を検知する。
- 添付バイナリ本体の最終的な保管キーは §4.8 / §11.2（`attachments/sha256/...`）に従う。landing zone は **生 Zip の退避専用**で、添付の重複排除済みストアとは別レイヤとして扱う。

**保持ポリシー**: 生 Zip は直近 N 世代（例: 全件 3 世代 ＋ 差分 90 日）を保持し、それ以前はライフサイクルで削除（具体値は §12.8 で決定）。

### 12.5 取得管理テーブルと完全性検証

§4.9 の `ingest_run` / `ingest_law_event` に加え、**ダウンロード成果物の記録テーブル `download_artifact`** を設ける。

```
TABLE download_artifact
  id              BIGSERIAL PRIMARY KEY
  ingest_run_id   BIGINT REFERENCES ingest_run(id)
  file_section    SMALLINT      NOT NULL          -- 1 | 2 | 3
  category_cd     TEXT                             -- file_section=2 のとき
  update_date     DATE                             -- file_section=3 のとき
  only_xml        BOOLEAN       NOT NULL
  source_url      TEXT          NOT NULL
  object_key      TEXT          NOT NULL           -- landing zone の生 Zip キー
  sha256          BYTEA         NOT NULL           -- 取得物の同一性判定
  byte_size       BIGINT
  http_status     SMALLINT
  law_count       INTEGER                          -- 展開して数えた法令フォルダ数（期待値）
  fetched_at      TIMESTAMPTZ   NOT NULL
  INDEX (file_section, update_date)
  INDEX (sha256)
```

**完全性検証（Stage 5）の考え方**:

- `download_artifact.law_count`（Zip 内の法令フォルダ数 = 期待値）と、当該 `ingest_run` における `ingest_law_event` の `action IN ('inserted','updated','skipped')` 件数（実績）を突合する。
- 差分が出た法令 ID を `ingest_law_event.action='failed'` から抽出し、子ジョブを再投入（§11.3）。
- **同一 `sha256` の Zip を再取得した場合は Stage 1 以降をスキップ**できる（前回成功と同一データ）。冪等性の最終防壁。

### 12.6 添付ファイルの取得方針

確定スコープでは取得形式を XML（`only_xml_flag=true`）中心とするが、§4.8 で添付（Fig の画像・様式）を S3 に保持する要件があるため、添付の取得経路を定める。

- **第 1 候補**: 全件取得時のみ `only_xml_flag` を**外して**画像・様式同梱の Zip を取得し、展開時に `pict/` 配下のバイナリを §4.8 の `attached_file` ＋ S3（`attachments/sha256/...`）へ流す。差分（日次）は XML のみとし、添付に変化があった法令は次回の全件取得で吸収する。
- **代替**: 全件・差分とも XML のみで取得し、添付は必要時に API v2 `/attachment/{revision_id}` から個別取得（チャネル B の限定利用）。

XML 中の `Fig.src`（`./pict/...`）と展開した添付バイナリの対応付けは §4.7-7 / §4.8 に従う。全件 Zip のサイズが「全データ」だと大きく膨らむため（§12.2.2）、**XML のみ取得 ＋ 添付は別取得**にするか **全データ一括**にするかは、初回の実サイズ計測後に §12.8 で確定する。

### 12.7 取得の堅牢性と礼儀正しさ

`/bulkdownload` はリクエスト数こそ少ないが、**1 本が GB 級**になるため取得処理は以下を満たす。

- **ストリーミング受信**: レスポンスを全展開せず、チャンク単位で landing zone（S3 マルチパートアップロード）へ流す。プロセスメモリに Zip 全体を載せない。
- **タイムアウトと再試行**: 接続・読み取りタイムアウトを分け、指数バックオフ（§11.7 の Procrastinate `retry`）で再試行。HTTP `Range` による再開可否は実機確認のうえ、不可なら最初から取り直す。
- **礼儀**: 明示的な `User-Agent`（プロジェクト名 ＋ 連絡先）を付与。同時取得は 1 並列（全件は元々 1 本）。`429` / `503` を尊重し `Retry-After` に従う。
- **失敗時の不変条件**: Stage 0 が途中失敗した場合、不完全な Zip は `download_artifact` に成功記録を残さない（`http_status` と sha256 で完全取得を確認してからコミット）。

### 12.8 スケジューリング

| 種別 | トリガ | 内容 |
|---|---|---|
| 初回ブートストラップ | 手動 1 回ジョブ | `file_section=1` 全件取得 → 全 Stage |
| 日次差分 | Procrastinate `@periodic(cron="0 3 * * *")`（§10-5） | `file_section=3&update_date=昨日` を取得 → 全 Stage |
| 全件リフレッシュ | 低頻度（例: 月次 or 手動） | `file_section=1` を再取得し、`sha256` 差分があれば再投入。差分取りこぼし・廃止反映の安全網 |

差分提供が過去 3 か月に限られるため、**日次運用していれば取りこぼしは発生しない**（§10-5）。万一の欠落に備え、低頻度の全件リフレッシュを安全網とする。

### 12.9 体積見積もり（暫定）

- 現行法令: 約 1 万件。
- 全件 Zip（XML のみ）: GB 級（分類別サイズの合算規模、§12.2.2）。
- 添付込み「全データ」: さらに増（画像・様式 PDF/JPG 由来）。
- DB 側の `law_node` 行数: 1 法令あたり数百〜数万行 × 1 万件で **数百万〜数千万行**規模（§11.1 と整合）。

正確な数値は初回取得で計測し、本節を更新する。

### 12.10 残課題 / 要実機確認

実装着手前に、初回の実機取得で以下を確定する。

1. **Zip 内構造の確定**: フォルダ階層・命名規則・添付の格納先（`pict/` か否か）・文字コード。パーサ（§8）のフィクスチャに固定する。
2. **全件 Zip が現行のみか廃止法令を含むか**: 公開ページに明記がない。含む場合は、取り込み時に `repeal_status` 等で**現行のみへ絞り込むフィルタ**を Stage 3 に入れる（確定スコープ「現行の有効な法令のみ」を満たすため）。判定材料（XML 中の廃止情報の有無）も併せて確認する。
3. **添付取得の方式確定**: XML のみ ＋ 添付別取得 か、全データ一括か（§12.6）。初回の実サイズ計測で判断。
4. **`Range` 再開の可否**: §12.7 のストリーミング再試行設計に反映。
5. **landing zone 保持世代数**: 全件・差分それぞれの保持ポリシー確定（§12.4）。
6. **全件リフレッシュ頻度**: 月次か手動か（§12.8）。
7. **生成タイミング**: e-Gov 側が全件 Zip / 差分をいつ再生成するか（差分取得の基準日と整合させる）。
